| 步骤 | 行为 | 硬编码/动态 |

| Install / Build / Test | 标准 nx 链 | — |
| Get version | 从 `apps/cli/package.json` 读出主版本号 | 单一来源 |
| **Verify uniform family version** | 遍历 **硬编码 9 个目录**，比对每个 `package.json` 的 `version` 与主版本号是否一致；不一致即 fail | 硬编码 |

| **Publish to npm** | 遍历 **硬编码 10 个目录**，`pnpm pack` → `npm view` 幂等检查 → `npm publish --provenance` | 硬编码 |

## 6. 当前 CI 流程的 5 处结构性缺陷

| # | 位置 | 缺陷描述 |
|---|---|---|
| 1 | `Verify uniform family version` 步骤 | 硬编码 9 个目录（`apps/cli` 被作为 version 主来源时未列入比对、`packages/hmr` 完全缺失） |
| 2 | `Publish to npm` 步骤 | 硬编码 10 个目录（`packages/hmr` 缺失）—— 新增包不会被自动发布 |
| 3 | `Publish to npm` 步骤的 `npm view "$name@$version"` 幂等跳过 | 如果某次发布中途失败，下一次从同 commit 重跑会因为"版本号已存在"而整体跳过，导致补发逻辑失效 |
| 4 | Tag 创建步骤 | tag 在 `Publish to npm` 之前就创建并推 origin；一次失败会留下"tag 已存在但部分包没发"的孤儿状态 |
| 5 | 缺少依赖闭包预检 | 不验证"包 A 声明的 `^0.3.3` 依赖是否真的在 registry 上"——一旦漏发，错误只会从下游用户的 npm install 报错才暴露 |

## 7. 当前依赖闭包（来自 `apps/cli@0.4.0` 的实际依赖）

```
@flowot/nx-pn@0.4.0
  └─ @flowot/nx-pn-host@workspace:^
       ├─ @flowot/nx-pn-storage-domain@workspace:^
       │    └─ @flowot/nx-pn-storage@workspace:^
       ├─ @flowot/nx-pn-storage-json@workspace:^   (可选 backend)
       ├─ @flowot/nx-pn-storage-sqlite@workspace:^ (可选 backend)
       ├─ @flowot/nx-pn-core@workspace:^
       └─ @flowot/nx-pn-client@workspace:^
```

拓扑顺序（family 内部）：`storage` → `{storage-json, storage-sqlite, storage-domain}` → `core` → `client` → `host` → `{apps/web, apps/cli}` → `apps/nx-pn`。
